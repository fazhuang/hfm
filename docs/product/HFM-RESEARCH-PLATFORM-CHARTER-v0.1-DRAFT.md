## 1. 定位

> 一个**研究工作台**，让研究者在一处完成"找材料 → 读原文 → 标注 → 关联 → 立论 → 引证 → 导出"的全流程，并且每一步的产出都带得住出处。

**它不是资料库。**资料库是"我放东西，你来查"；工作台是"你在这儿干活，成果带走"。

**服务对象**：教授、学生、爱好者。

**数据范围**：585 件研究资料（论文 515 · 现代出版物 70）。

## 2. 第一性原理

人文学术研究的实际操作，剥掉工具与形式，是七件事：

| # | 动作 | 研究者的原话 |
| :--- | :--- | :--- |
| 1 | 找到材料 | "哪几篇讲过这个问题" |
| 2 | 读材料 | "原文怎么说的" |
| 3 | 标记材料 | "这段我要记住" |
| 4 | 建立关联 | "这条和那条是什么关系" |
| 5 | 形成论证 | "我的判断是这样，依据是这些" |
| 6 | 引用 | "这句话出自哪一篇哪一段" |
| 7 | 产出 | "带走一份能用的东西" |

平台的成败判据：**这七件事能不能在一处完成，且每一步都带得住出处。**

## 3. 核心隐喻：项目即容器

```
研究项目 Project
  ├── 材料集     从 585 件研究资料中挑进来的
  ├── 标注       在原文段落上做的划线批注
  ├── 笔记       自由记录
  ├── 论断       我的观点 + 我引的证据
  └── 引文表     规范化引用，可导出
        ↓
      导出（文本 / 打印 / 引文表）
```

**一切研究动作都在项目内发生。**研究者打开平台，先选项目，再干活。这是与"浏览资料"的根本区别。

现有模型已具备 `ResearchProject` / `ResearchNote` / `ResearchAnnotation` 三张表，方向正确，需扩展。

## 4. 四层能力（建设顺序，非功能清单）

### L1 — 可读

研究者能**打开并阅读这 585 件资料**。

- 检索：题目、作者、关键词、篇卷
- 阅读：影印件 + 抽取文本（现有 `passages` 1007 段）
- 分层：元数据层（题录）+ 全文层

**这是地基。**没有 L1，L2–L4 全部落空。

### L2 — 可标

在原文段落上**划线、批注**，标注归属到项目。

`research_annotations` 表已存在且字段完整（`passage_id / quote_text / start_offset / end_offset`），**只差界面**。

### L3 — 可引

**这是当前断得最狠的一环。**

```
citations 23 条，passage_id 全为空
```

引文定位不到原文段落 —— 平台现在**做不出一条能回溯到原文的引证**。而引证恰恰是人文学术研究的核心产出。

L3 要做：标注 → 一键生成规范引文 → 引文永远带得住篇 / 章 / 段位置。

### L4 — 可产出

项目导出：文本、打印格式、**引文表**。前端已有 `ExportPanel.vue`，需扩充至覆盖引文表。

## 5. 三类研究者

**不做三套系统。做一套工作台，能力渐进开放。**

| 角色 | 他们做的 | 能力 |
| :--- | :--- | :--- |
| 爱好者 | 读、标、收藏 | L1 + L2 |
| 学生 | 读、标、引、交作业 | L1 + L2 + L3 + 导出 |
| 教授 | 全部，长周期项目，建材料集 | L1–L4 + 项目管理 |

理由：三类人做的是**同一件事的不同深度**，不是三件不同的事。分三套会立刻产生三套维护成本。

## 6. AI 引入架构

### 6.1 约束（实测）

项目有一条**冻结的架构边界**直接管 AI：

```
AB-16 | Deferred modules | FORBIDDEN_COUPLING
Display, HFB UI reuse, AI, 3D, VR, XR, and virtual training
may not add dependencies to the Phase 1 core.
```

机器守卫另有 import 扫描（`guardrails.py:41`，覆盖 `src/hfm/phase2/`，拦截 `torch|openai|anthropic|langchain|transformers`）。

**关键推论：AB-16 禁止的是「耦合」，不是「能力」。**问题不是"要不要用 AI"，而是"AI 放在哪里"。

### 6.2 第一性原理

> 人文学术平台的核心价值 = 可追溯。
> LLM 的默认失败模式 = 自信地编造。
> 两者直接冲突。

**架构的第一目标不是"AI 多能干"，而是：让模型的输出在结构上永不可能冒充史料。**

### 6.3 三层隔离 + 独立服务

```
史料层  documents · passages · editions     只读，AI 无写权限
   ↓ 单向只读
AI 服务（独立进程 · HTTP · 不进核心）        不 import 任何 LLM SDK
   ↓
模型输出层  ai_outputs                      永久标记 ai_generated，视觉可区分
   ↓ 研究者显式采纳
研究层  projects · annotations · citations   研究者的产出
```

四条硬规则：

1. **AI 不进核心。**独立部署，核心通过 HTTP 调用。核心代码不出现 LLM SDK —— AB-16 与机器守卫同时满足。
2. **单向只读。**AI 服务对数据库只有读权限。
3. **输出隔离。**模型产出只进 `ai_outputs`，**永不写入** `documents / passages / assertions / citations`。这是结构性保证，不是纪律要求。
4. **视觉可区分。**AI 内容与史料样式必须不同，研究者一眼能分清哪句是古人说的。

### 6.4 能力分级

| 能力 | 研究价值 | 幻觉风险 | 判断 |
| :--- | :--- | :--- | :--- |
| 语义检索 | 高 | **零** | **首先做** |
| 文言文辅助（注音 / 释义 / 白话） | 高 | 中 | 做，强制标注 |
| 摘要与主题聚类 | 中高 | 中 | 做，标注 |
| 基于语料的问答（RAG） | 高 | **高** | **最后做**，强制引用，无源拒答 |
| 替研究者立论 | — | 最高 | **不做** |
| 临床建议 | — | — | **不做**（CR-005 + `P2-CLINICAL=REJECTED`） |

**AI 在研究平台里的定位：放大器，不是作者。**

### 6.5 语义检索为何先做

研究者问"哪些篇章讨论了情志病"：

| | 做法 | 结果 |
| :--- | :--- | :--- |
| 现状 | 关键词匹配 `情志` | 漏掉只写"郁证""惊悸"的段落 |
| 语义检索 | 向量相似度 | 全部找出，**返回原文段落本身** |

返回的是 `passages` 表里的原文，不是模型写的话。模型只负责"找"，不负责"说"。**零幻觉，且本地计算。**

### 6.6 合规：语料不出库 + 最小外发

| 层 | 在哪跑 | 外发内容 |
| :--- | :--- | :--- |
| 向量化 / 检索 | 本地 | **零** |
| 生成（翻译 / 摘要 / 问答） | 第三方 API | **仅命中的段落**，非整库 |

**技术前提（实测）**：`hfm_prod` 当前无 pgvector（PostgreSQL 16.14）。需补向量能力。

**模型接入做成可配置**，客户要求时可换国产模型或本地部署，不动业务代码。

### 6.7 学术诚信作为平台功能

研究者用了 AI，论文里必须声明。平台应替他记：

- 记录每次 AI 调用：模型、版本、时间、输入、输出
- **项目导出时自动附「AI 使用说明」**

这一条使 HFM 与同类平台区分开：别人把 AI 当插件，这里把 AI 的**可声明性**当成平台能力。

### 6.8 接口形态（研究平台内部，登录后）

```
POST /api/v1/research/ai/search       语义检索      ← 本地，零外发
POST /api/v1/research/ai/gloss        文言辅助      ← 外发命中段落
POST /api/v1/research/ai/summarize    摘要          ← 外发单篇
POST /api/v1/research/ai/ask          语料问答      ← 外发命中段落，强制引用
GET  /api/v1/research/ai/usage        本项目 AI 记录
```

**公众门户不开放任何 AI 端点。**

## 11. 对标结果（第 10 节第 1 步，2026-09-15）

搜索并核实了 GitHub 上的同类项目。以下四项与 HFM 的契合度最高。

### 11.1 FoJin 佛津 — 同类中最重要的参照

[`xr843/fojin`](https://github.com/xr843/fojin) · Apache 2.0 · 2,096 commits · 341 stars

**技术栈与 HFM 几乎完全一致**：FastAPI + PostgreSQL 15 + pgvector(HNSW) + Elasticsearch 8 + Redis 7 + Nginx。前端为 React 18。

它已经解决了本宪章第 6 节提出的核心难题 —— **如何让 AI 的引用可信**。做法是三道**确定性**校验（不是提示词工程）：

| 守卫 | 机制 |
| :--- | :--- |
| **引用白名单** | 引用若不在本次实际检索到的来源中，被剥离或纠正 |
| **逐字校验** | 引号内的文字必须是检索段落的**逐字子串**（繁简折叠）；不逐字的降级为普通叙述 |
| **信任状态** | 每个回答标注 `verified` / `citation_corrected` / `quote_relaxed` / `no_sources` |

并有回归门禁指标 `served_trustworthy_rate` 与 `verbatim_quote_rate`（分列报告，防止"少引用"来刷分），以及一个公开的 `/api/verify/quote` 端点做字符级差异校验。

规模：10,500+ 文献、670K+ 向量、110K+ 实体、28,000 关系。也已发布只读 MCP server。

> **对 HFM 的意义**：本宪章第 6 节的原则（"输出隔离""无源拒答"）方向正确，但**停留在原则层面**。FoJin 给出了可落地的机制，且用的是 HFM 已有的技术栈。

### 11.2 史记知识库 — 段落编号与实体着色

[`baojie/shiji-kb`](https://github.com/baojie/shiji-kb) · 脚本 MIT / 标注数据 CC BY-NC-SA · 1,570 commits · 2.8k stars

把《史记》57.7 万字转化为可浏览知识图谱。要点：

- **22 类实体语法高亮**，读者可一键开关且偏好持久化；实体可点击跳转索引
- **Purple Number 段落编号** —— 每个段落有稳定、人可读的编号
- 14,065 实体词条 / 126,441 标注实例 / 3,198 事件 / 7,637 关系
- 方法论文档：14 个元技能 + 89 个流水线技能（共 103 个），含九步流水线（校勘 → 结构分析 → 实体构建 → …）
- 四层语义模型：结构语义 → 图谱语义 → 知识语义 → 应用语义

> **对 HFM 的意义**：**Purple Number 正是 `citations.passage_id` 全空那件事的解药。**段落必须有稳定的、人类可读可引用的编号 —— UUID 不能出现在论文脚注里。

### 11.3 观自在 — 阅读器形态参照

[`AmigaMeow/guanzizai`](https://github.com/AmigaMeow/guanzizai) · Next.js / React / TypeScript

面向古籍与公共领域文本的阅读平台。功能清单与本宪章的 L1–L4 高度重合：原文/释文/平行对照阅读、分卷目录、**段落定位**、站内搜索、**阅读导出**、书架收藏、**基于已发布内容检索的问答与出处卡片**、译文生成与人工审核流程。

> **对 HFM 的意义**：验证了 L1–L4 的分层方向；它的"出处卡片"是引文展示的具体形态。

### 11.4 CATMA — 标注体系的学术范式

[`forTEXT/catma`](https://github.com/forTEXT/catma) · GNU GPLv3

面向人文学者的协作标注与分析平台，明确区分两种标注范式：**taxonomy-driven（自上而下，按分类体系）** 与 **hermeneutic（自下而上，诠释驱动）**。

> **对 HFM 的意义**：HFM 现在的标注只有自由文本。学术标注是**有类型**的。

## 12. 优化提案（第 10 节第 2 步，待审计）

对标后识别出八项对当前方案的强化。**均为提案，未经审计前不构成方案。**

| # | 提案 | 来源 | 影响的章节 |
| :--- | :--- | :--- | :--- |
| **O-1** | **段落永久编号**：每段 passage 获得稳定、人可读、可引用的编号（如 `甲乙经-卷三-篇七-§12`）。**这是 L3 引证能成立的前提** —— UUID 不可能出现在论文脚注里 | shiji-kb | §4 L3 |
| **O-2** | **AI 引证三重校验**：引用白名单 + 逐字子串校验 + 信任状态标记，配回归门禁指标。把"无源拒答"从原则变成机制 | FoJin | §6.4 §6.8 |
| **O-3** | **实体着色阅读**：读原文时人物/书名/术语直接着色可点。HFM 已有实体与术语数据，只是未在正文中可视化 | shiji-kb | §4 L1 |
| **O-4** | **标注类型体系**：在自由批注之上加一层分类（异文 / 典故 / 医理 / 纪年 / 存疑…），支持 taxonomy 与诠释两种范式 | CATMA | §4 L2 |
| **O-5** | **向量层选型复核**：FoJin 用 pgvector(HNSW) 且技术栈与 HFM 一致；但 **HFM 已有 Elasticsearch**，语义检索可能走 ES 而非新增 pgvector。需在优化阶段比较，避免多引入一个组件 | FoJin / 殆知阁 | §6.6 §9-F |
| **O-6** | **出处卡片**：引文展示为可展开卡片，原文对照，而非一行脚注 | 观自在 / FoJin | §4 L3 L4 |
| **O-7** | **标注成果可否共享**：Kanripo 的 fork/merge 模型允许学者共享标注。HFM 现为私有孤岛 —— 这是产品决策，需授权方裁决 | Kanripo | §3 §5 |
| **O-8** | **多源冲突处理**：人文学科的核心问题之一（同一事件在不同史料中记载不一）。HFM 现有模型无此表达 | Sho / CHisIEC | §2 §3 |
